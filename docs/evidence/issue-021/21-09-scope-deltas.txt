ISSUE-021 — deltas between plan.md and what was executed, each with its reason

Four work items in plan.md were written before the board's other issues landed. By the time
ISSUE-021 executed, the world had moved. Every deviation is listed here rather than left for a
reader to discover.


DELTA 1 — WI-1: the schema was VERIFIED, not applied.
plan.md said: clone elephant-query-db, apply migrations/*.sql with psql, run ensure-folio-constraint.
what happened: ISSUE-030 had already applied all seven migrations and recorded a
  pipeline_schema_migrations ledger. Re-applying blindly was explicitly ruled out. WI-1 read the
  ledger, verified all seven tables and the parcels_jurisdiction_key_request_identifier_unique
  constraint, and recorded the evidence. npm ci was run in the clone; git status in the clone is
  clean, so the read-only checkout was never edited.
evidence: 21-01-schema-tables.txt, docs/query-db-setup.md


DELTA 2 — WI-2 and WI-3: NO BULK LOAD WAS RUN, for any track.
plan.md said: run `npm run load:bulk --tracks appraisal`, then `--tracks permits`.
what happened:
  - appraisal: ISSUE-018's per-parcel ingest is a durable Restate workflow that was ALREADY loading
    these exact artifacts into parcels under source_system=rock_island_appraiser and was STILL
    RUNNING throughout ISSUE-021, climbing at ~1.5 parcels/s toward 65,955 over ~11 hours. Starting
    a second writer against the same source_system would be a concurrent double-load of the rows
    ISSUE-018 is upserting, and the kit skill's rule is a single-writer Loader per county. The load
    was VERIFIED instead, with the kit's own validate-appraisal-folio.ts.
  - permits: ISSUE-019 had already loaded 25,354 permit records into permits_rock_island_city, the
    table carrying the permit-to-parcel link columns. A --tracks permits load would have written the
    same records a second time into property_improvements.
  - geo: ISSUE-020 had already loaded all seven clipped signal sources.
consequence, and how it was handled: the parcels table is a MOVING PARTIAL SUBSET. Reconciling over
  it would have produced county metrics from an incomplete corpus. All reconciliation therefore runs
  over the per-parcel source mirror — all 65,955 records, verified equal to the live FeatureServer
  count by scripts/reconcile-before-load.mjs. Every published metric names the corpus, the record
  count and the timestamp. The only figure taken from parcels is the provenance coverage, and it is
  published with its row count and timestamp and an explicit "this is not the county total".
evidence: 21-02-load-log.txt, 21-02-folio-validation.txt, 21-03-permit-load-log.txt,
  21-03-track-counts.txt


DELTA 3 — WI-2 acceptance cannot pass while ISSUE-018 is still running.
plan.md acceptance: validate-appraisal-folio.ts exits 0 with distinct_folios = 65,955.
what happened: it exits 1 on assertion 1a — distinct_folios was 2,479 at capture time, because the
  ingest had reached that far. That is an INCOMPLETENESS report, not a collapse report, and it is
  recorded verbatim rather than smoothed. The two assertions this issue actually exists to guard —
  total_parcels == distinct_folios (no collapsed folios) and orphaned_properties == 0 (the collapse
  symptom) — both PASS, and they are independent of how far the load has progressed. The acceptance
  will pass unchanged once ISSUE-018 finishes; nothing in this issue needs to change for it to.
evidence: 21-02-folio-validation.txt (both runs, verbatim)
